# Fichas personalizadas

O mestre escreve um **modelo** de ficha (uma lista de arquivos HTML, CSS e JS, com fontes e imagens próprias) na biblioteca e cria **fichas** daquele modelo, também itens da biblioteca (nome, pasta). A ficha pode ficar **sem dono** (só mestres a veem), ir a um **jogador** (fica no personagem dele, com token no grid ou sem) ou a um **token**; um personagem ou token pode ter várias. A ficha roda num iframe isolado (origem opaca, sem rede) e só fala com a mesa pelo SDK `window.lorkarium`, por um `MessagePort`; o host traduz cada pedido num comando real e o servidor reautoriza tudo. Produto: [`../spec.md`](../spec.md) §3.13.

> **Detalhe em [`sheets/`](sheets/) e nos arquivos do client abaixo — abra só o arquivo da tarefa.**

## Regras de negócio

- **Princípios de toda capacidade do SDK:** age só sobre o dono da ficha (o host escolhe, nunca o frame); nunca faz mais do que quem olha a ficha faria à mão (o servidor reautoriza); valida o DTO nas duas pontas e tem limite de frequência; bytes chegam pela porta, nunca URL nem cookie; o modelo declara o que usa e o host recusa o resto.
- **Dado gravado nunca executa:** o frame só roda os scripts que o host embutiu, listados pelo SHA-256 (CSP em [`sheets/sandbox.md`](sheets/sandbox.md)); HTML vindo dos valores, mesmo mostrado por `innerHTML`, não roda `on*`, `<script>` nem `javascript:`.

- Sem "modo seguro": a medição de processo (laço infinito na ficha × processo do frame no Chrome e na casca) não foi feita; o procedimento está em [`sheets/sandbox.md`](sheets/sandbox.md). Até lá, uma ficha travada só é contida pelo cão de guarda ("A ficha não respondeu").
- Exportar e importar modelo (`.lksheet`) é só do mestre: exporta sempre a versão salva e importa sempre como modelo **novo**, pelo `POST` de sempre; o código importado roda na mesma sandbox, sem exceção.
- O console da ficha na sala é só de quem gerencia (`canManage`, o mestre); o jogador não recebe linha nenhuma.

## Armadilhas

- **Nonce herda para `import()`: o CSP da ficha usa hash, nunca nonce** (o `import()` de CDN saía para a rede; detalhe em [`sheets/sandbox.md`](sheets/sandbox.md)).
- **Ficha em janela travava no cão de guarda ("A ficha não respondeu"):** o portal desenha o frame na auxiliar, mas o `postMessage` da porta sai do código da janela da sala, então o `event.source` no frame é a sala e não o `parent`. O bootstrap exigia `source === parent`, descartava a porta e o `ready` nunca saía. Agora aceita qualquer janela fora do frame (`sheet-bridge-bootstrap.spec.ts`, "not its parent"); a prévia do editor em janela também passou a funcionar. Spec com fake de janela precisa de `parent` (o `FrameWindowRefFake`, ele mesmo no topo).
- **Vazamento no e2e se conta na rota, não no `page.on('request')`:** o Chromium dispara `request` também para o pedido que o CSP barra (seguido de `requestfailed` com `csp`). Quem prova "nada saiu" é um `context().route` para tudo que não é `localhost`, que só vê o que chegaria à rede.
- **O modelo do e2e nasce do código inicial do client** ("Novo modelo de ficha" → `STARTER_SHEET_SOURCE`: PV, "Força", "−5 PV", "Rolar ataque"); o e2e só digita o nome. Mudar o código inicial (ids `#pv`, rótulos, `1d20+5`, salvar no `change`) quebra o `sheets.spec.ts`. Código que exigiria digitar no CodeMirror vai pela rota `POST …/sheet-templates`. O "−5 PV" acha a barra pelo **nome** (`bars.adjust('PV', …)`): o token do e2e precisa de uma barra "PV" (e só uma).
- **O "Força" do código inicial salva no `change`:** `fill` sozinho não salva; o e2e sai do campo com Tab e confere pela rota `GET …/sheets/:s` antes de recarregar (o `dispose` manda o lote pendente sem esperar resposta).
- **O Caio só abre a ficha pelo card "Na mesa"** ("Abrir ficha de Lyra", com uma ficha; com várias o único ícone do card é o menu "Fichas de Lyra"): o menu do token é só de quem controla.
- **Criar a ficha pelo menu abre a aba dela para o mestre e esconde o tabuleiro:** feche a aba ("Fechar Ficha · <nome da ficha>", o nome padrão é "<modelo> · <token>") antes de clicar no tabuleiro de novo.
- **O título da aba é o nome da ficha, não o do token**, e segue o nome salvo: spec que abre uma ficha pelo fake precisa que o `detail` devolva o mesmo nome (`serverSheetIs`), senão a aba muda de nome ao carregar.
- **O card "Na mesa" lista as fichas do personagem, não as do token:** a ficha feita no menu de um token **solto** fica no token e não aparece no card de ninguém; a de um token ligado vai ao personagem. O e2e liga a Lyra ao personagem da Bia (`createCharacterTokenWithPv`, pelo `linkCenterTokenToCharacter` de `e2e/test/support/token-cards.ts`) antes de criar a ficha; sem isso o Caio nunca acha o "Abrir ficha de Lyra".
- **O nome da ficha é o título de tudo no e2e** (aba, região, `iframe`, aviso de 404, item da árvore): os helpers recebem o nome confirmado pela resposta do `POST …/sheets`, nunca o nome do token.
- **Ctrl+S dentro da prévia não salva:** o frame é outro documento (origem opaca) e o atalho escuta só o documento do editor; o e2e aperta com o foco no código ou no nome.
- **A linha do erro no console é de um arquivo `.js`** ("(a.js, linha 3, coluna 9)"), só quando a posição cai num JS do autor; o e2e que conferir a linha precisa do erro num JS.
- **Atributo `on*` não roda na ficha** (`onclick`, `onerror`, `onchange`… no HTML do modelo ou dos dados): o CSP tem `script-src-attr 'none'`. Modelo antigo com `onclick` para de responder ao clique sem erro na tela (só a violação no console do navegador); o autor liga o evento por `addEventListener` no JS. Pelo mesmo motivo `href="javascript:…"` não faz nada, e um `<script>` escrito num `.html` (sem hash na política) não roda: script só nos arquivos `.js`. Ao salvar, o editor avisa a linha de cada `on*`/`javascript:` ([`client/sheet-template-editor.md`](client/sheet-template-editor.md)).
- **Ficha que escreve no personagem só depois de uma edição de quem a tem** (a de Lork: CA, CD e o máximo de HP/MP/EN/ES): calcular e gravar a cada `state` faria abrir a ficha reescrever o que o mestre mudou à mão no card, e duas fichas abertas brigariam. O modelo marca "sujo" no `input` e manda `character.set`/`bars.adjust` 600 ms depois, só se o valor calculado difere do da mesa (o host ainda pula o igual sem contar no limite).
- **`data-lk` em `contenteditable` mostra o HTML como texto quando o campo vira `contenteditable="false"`** (a regra lê o atributo): uma ficha que desliga a edição de quem só lê liga o texto rico por conta própria (`innerHTML = lorkarium.html.sanitize(valor)`, sem sobrescrever o campo com foco) e deixa `data-lk` para os campos simples.
- **Listas nos valores são objetos por id, não arrays** (`lorkarium.lists`): o `jsonb` não guarda a ordem das chaves, então cada item leva um `ordem` (o `Date.now()` da criação) e a ficha ordena por ele. A ficha de Lork remonta uma lista só quando os ids mudam; o resto do `state` é pintado por cima, para não tirar o foco de quem digita.
- **Os bytes do retrato chegam numa cópia nova a cada `state`:** comparar o `ArrayBuffer` por identidade recria o `blob:` sempre; compare tipo e tamanho.
- **Os scripts do modelo são clássicos e dividem um escopo:** `const`/`let` de um arquivo valem nos seguintes, mas só depois que o arquivo rodou (TDZ); chame tudo do último arquivo. Por isso o modelo da ficha de Lork fica fora do ESLint (`no-undef` entre arquivos) e o Vitest o roda concatenado num corpo só.
